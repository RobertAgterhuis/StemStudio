## 2. Refused worker submissions become `failed` (sections, score views, setlist PDF)

- **Sections** (`SectionService`): a 4xx from `POST /v1/section-jobs` (`WorkerRequestException`, e.g. 404
  input-not-found or an unknown route on an older worker) now stores `status failed` with
  `error = "The processing service could not start finding the sections: <worker detail>"`
  (`SectionService.SubmitRejected`). `detectSections` answers **202 with that failed set** (the schema
  allows `failed`; the UI shows it and offers retry; a retry POST is allowed because `failed` is not
  detecting). The automatic trigger after a separation stores the same and does not retry by itself.
  An unreachable worker (`WorkerUnavailableException`) is unchanged: 503 `worker-unavailable`, status `none`.
- **Score views** (`ScoreViewService`): same pattern: a refused job stores the view `failed` with
  `ScoreViewService.SubmitRejected + detail` (both `createScoreView` -> 202 failed, and the automatic view of
  a new score); a POST retries (existing rule: failed views are re-submitted).
- **Setlist PDF** (`SetlistPdfService`): a refused job is 503 `document-failed` with the worker's detail
  (was 503 `worker-unavailable`). Worker failures map through one `ProblemOf` switch.
- data-model 3.3 (`specs/014-practice-flow/data-model.md`) gained the rule.
