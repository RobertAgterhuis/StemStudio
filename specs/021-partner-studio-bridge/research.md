## Part A - Practice partner (C9)

### R-01 ACE-Step 1.5 track-conditioned generation (lego / complete / extract)

Sources: <https://github.com/ace-step/ACE-Step-1.5> (README, DiT table),
<https://huggingface.co/ACE-Step/acestep-v15-base> (model card), arXiv 2602.00744 (ACE-Step 1.5
paper), Hugging Face Diffusers ACE-Step pipeline docs, ComfyUI "ACE-Step 1.5 Lego guider" docs.

Findings:

- ACE-Step 1.5 has six DiT task modes: `text2music`, `cover`, `repaint`, `extract`, `lego`,
  `complete`. The README's DiT table marks **extract, lego and complete as supported only by the
  base models** (`acestep-v15-base` 2B, `acestep-v15-xl-base` 4B). `turbo` and `sft` (used by
  009/010: `acestep-v15-turbo`) do **not** support them.
- `lego` = "generate a specific track based on audio context" (Diffusers docs); `complete` =
  "complete an input audio with additional tracks"; `extract` = isolate one track. Track names come
  from 12 instrument classes: `vocals`, `backing_vocals`, `drums`, `bass`, `guitar`, `keyboard`,
  `percussion`, `strings`, `synth`, `fx`, `brass`, `woodwinds` (hosted-provider and ComfyUI docs;
  the README itself does not list them, so S-01 confirms the exact strings at the pinned commit).
- The paper (section 2.4/3.3) says an "Omni-Task Fine-tuning" phase on 6 million stem-separated
  tracks trains extraction, layering ("adding complementary instruments to a track") and
  completion by varying the source latent and mask. **No quality evaluation of these tasks is
  published.** The paper reports BPM, key, duration and structure as metadata generated by the LM
  and passed to the DiT; there is **no chord conditioning**.
- `acestep-v15-base`: MIT licence (model card), 2B parameters, BF16 safetensors, recommended 50
  inference steps, classifier-free guidance supported; quality "Medium", diversity "High" (model
  card). Size of the checkpoint is not stated; 2B BF16 is about 4 GB (estimate from parameter
  count; S-01 records the real size and SHA-256).
- The XL base (4B) needs >= 20 GB VRAM without offload or >= 12 GB with offload and quantisation
  (README); rejected for the 16 GB reference card (as ADR-018 D6 rejected XL turbo).
- The generator already pins ACE-Step at commit `ca1e85fe9430179831e6bc6be790c332190a3866`
  (`ports.ACESTEP_CODE_COMMIT`). Whether that commit's `generate_music` accepts
  `task_type="lego"` with a `track_name` is **[to measure] S-01**; if not, the pin moves to the
  first commit that does (MIT, same lock rules).

Decision: ACE-Step 1.5 base + lego (ADR-0211 D1). Output handling: S-01 also verifies whether the
lego output is the generated track alone or the full mix; if it is the mix, the engine runs a
second step `extract` with the same track name on the result (also base-only, same loaded model).

### R-03 Conditioning on key, tempo, sections and chords

- **Audio context** (the other stems, summed at unity by the generator as for restyle) carries the
  harmony, groove and form; it is the main condition of lego.
- **Tempo and time signature**: ACE-Step's `bpm` and `timesignature` parameters (used by 010).
  Source: the track's beat grid (001) - median BPM, time signature from the downbeat analysis.
- **Key**: ACE-Step's `keyscale` (010 uses it), from 016 key detection (`C major`, `A minor`, ...);
  a key change uses the key at the range start.
- **Chords**: no model input exists (R-01). The API writes the progression of the range into the
  caption in a compact form (`chords: Am F C G | Am F C G`, at most 160 characters, one bar per
  symbol, repeated patterns collapsed). Whether this text measurably helps is **[to measure] S-02**
  (A/B on 3 songs with and without the chord text, chord agreement of the fit check); if it does
  not, the builder keeps it out (one flag, no contract change).
- **Sections**: the range comes from 014 sections; the section label goes into the caption
  (`section: chorus`). Lego repaints only inside the range (`repainting_start/end`, as 009 in-place
  restyle), so the part starts and stops at the section boundaries.
- **Instrument description**: per family a fixed English caption fragment (data-model 3.2), plus
  the optional user hint after the imitation guard (ADR-018 D8).

### R-04 Fit check (worker, CPU)

The generated part must lock to the song; ACE-Step returns 48 kHz audio of the source length, but
no guarantee of sample alignment is documented. Method (all librosa 0.11, already in the worker):

1. Resample the take to 44.1 kHz (soxr, as the worker's ingest).
2. Onset strength envelope of the part (hop 512) vs the track's beat grid impulse train; offset =
   argmax of the cross-correlation within +-250 ms; confidence = peak / second peak.
3. Tempo drift: beat tracking of the part (`librosa.beat.beat_track` with the grid BPM as prior);
   drift = slope of (part beat - nearest grid beat) over time; > 20 ms per 30 s = "drifts".
4. Key agreement: Krumhansl-Schmuckler profile on the part's mean CQT chroma vs the song key
   (016); "agrees" when the same tonic and mode, or relative major/minor.
5. Chord agreement: per beat, cosine similarity of the part's chroma to the template of the 016
   chord at that beat > 0.5; share of beats over the range (only for pitched families; drums and
   percussion report `null`).
6. Loudness: RMS in dBFS over non-silent frames; "very quiet" below -45 dBFS; the gain to match the
   replaced stem (alternative mode) or the median of the other stems (add mode), clamped to +-12 dB.

Verdict: `good` (offset confidence >= 2, no drift, key agrees, chord agreement >= 0.6 or null),
`fair` (one criterion fails), `poor` (two or more fail, or very quiet). Deterministic and
unit-testable with synthetic fixtures (click track offset by 37 ms -> offset 37 +- 1 ms).

Placement: worker job kind `conform` (worker-api 1.12.0): it both measures and writes the
conformed 44.1 kHz FLAC, so the API never resamples. Rejected: fit check in the generator (it is a
GPU-only service, the check is CPU and must also work for re-conforming without a GPU), in .NET
(no DSP stack).

### R-05 GPU needs (provisional until S-01)

`acestep-v15-base` has the same 2B DiT size as turbo, so weights and VAE memory are as COVER_TURBO;
50 steps with CFG doubles the batch of the DiT forward pass. Provisional needs (ADR-018 D4 rule:
peak above idle + 1 GiB): `LEGO_BASE` 14,336 MiB, `LEGO_BASE_LOWMEM` 9,216 MiB (offload). Time per
60 s part: about 6x turbo steps plus CFG -> estimate 40-90 s warm on the RTX 5070 Ti. Both
**[to measure] S-01**; `profiles.py` takes the measured values (rounded up to 512 MiB) and SC-001 is
checked against them. The base DiT is loaded instead of turbo for partner jobs; the generator keeps
at most one DiT resident (switching costs a load, measured in S-01).

## Part B - Amp and pedal simulation (C10)

### R-06 Neural Amp Modeler core and browser builds

Sources: <https://github.com/sdatkinson/NeuralAmpModelerCore> (MIT), NAM model file specification
<https://neural-amp-modeler.readthedocs.io/en/latest/model-file.html>,
<https://github.com/tone-3000/neural-amp-modeler-wasm> (MIT), npm `neural-amp-modeler-wasm`
(3.0.7, 2026-10-30), TONE3000 "NAM web player" blog, Emscripten Wasm Audio Worklets docs.

- **NeuralAmpModelerCore** (Steven Atkinson, MIT) is the C++ DSP library that loads `.nam` files
  and runs inference (WaveNet "A1", LSTM, ConvNet, Linear; newer core versions add the "A2"
  architecture and slimmable models). Dependencies: Eigen (MPL-2.0, header-only, unmodified),
  nlohmann/json (MIT), AudioDSPTools (MIT, includes the resampling container used by the NAM
  plugin).
- The TONE3000 fork `neural-amp-modeler-wasm` (MIT) compiles the core with Emscripten into a
  **single-threaded module with a plain C API** and a hand-written `AudioWorkletProcessor`;
  **no SharedArrayBuffer and no COOP/COEP headers** are needed; 64 MB initial WASM heap, 512 MB
  max. The npm package (3.0.7) exports `./engine`, `nam-worklet.js` and `nam-engine.wasm`, but has
  runtime dependencies `lucide-react`, `react-knob-headless` and peer dependencies React 18.
- Decision (ADR-0212 D2): StemStudio does **not** add the npm package (React runtime dependencies
  in a framework-free engine; its release cadence of 9 versions in 4 days in October 2026 is a
  stability risk). It builds the NeuralAmpModelerCore at a pinned commit with a pinned Emscripten
  (`emscripten/emsdk` image) and its own ~100-line C shim (`nam_create`, `nam_process`,
  `nam_reset`, `nam_latency`, `nam_destroy`, the same approach as the fork), with `-msimd128 -O3`,
  no threads. The `.wasm` binary (expected 300-800 KB) is committed under
  `src/audio-engine/vendor/nam/` with a `PROVENANCE.md` (core commit, emsdk version, build command,
  SHA-256) so `npm test`, the app build and CI need no Emscripten; a CI job rebuilds it in the
  container and compares exports and the golden vectors (not bytes; Emscripten output is not
  guaranteed byte-reproducible).
- Loading: the main thread fetches and compiles the module (`WebAssembly.compileStreaming`) and
  passes the `WebAssembly.Module` to the worklet in `processorOptions` (structured-cloneable in
  Chromium). The page's CSP needs `'wasm-unsafe-eval'` in `script-src` (012's SoundTouch WASM has
  the same need; devops/frontend check it is present once).

### R-07 CPU cost and model sizes

- `.nam` files are JSON with `version`, `architecture`, `config`, `weights` (flat float array),
  optional `sample_rate` and `metadata` (name, modeled_by, gear_type, tone_type, input/output
  levels). WaveNet captures come in the trainer presets "standard", "lite", "feather" and
  "nano" (smaller = cheaper); the file specification does not state parameter counts or CPU cost,
  so S-03 records file size and cost per preset. The NAM documentation does not give
  CPU figures; TONE3000 only says real-time inference "is a bit CPU-intensive".
- Budget used here: one render quantum = 128 frames = 2.90 ms at 44.1 kHz. The chain (resampler +
  NAM + IR convolution, which is a native `ConvolverNode` outside the worklet) must keep the
  worklet's `process()` below **50 % of the quantum** (1.45 ms) for a standard WaveNet on the
  reference CPU (SC-004). **[to measure] S-03**: the engine's benchmark page measures
  `process()` time percentiles (p50/p99) per architecture with the WASM SIMD build; if standard
  WaveNet exceeds the budget, the UI marks standard captures "heavy" and the catalogue prefers
  lite/feather entries. Pedal + amp = two NAM instances: both count against the budget.
- Overload detection: `performance.now()` is not exposed in `AudioWorkletGlobalScope`, so the
  cost per quantum is measured when a model loads, by running the same WASM module on 1 s of noise
  in a dedicated Web Worker; at run time the engine watches the context's underrun statistics where
  the browser exposes them (Chromium playout statistics, S-03 confirms) and falls back to coarse
  `Date.now()` deltas over 64-quantum windows in the worklet. `overloaded` = more than 2 % of quanta
  in a 2 s window over 90 % of the budget, or any reported underrun while the rig runs.

### R-08 Latency budget

| Part | Typical value | Source |
|---|---|---|
| Interface input + driver + browser capture (WASAPI shared) | 5-15 ms | Chromium on Windows, measured by 015's calibration (round trip) |
| One render quantum in, one out | 2 x 2.9 ms | Web Audio 128-frame quantum at 44.1 kHz |
| NAM inference | 0 (causal, no look-ahead) | NAM core |
| Resampler 44.1 <-> 48 kHz (AudioDSPTools Lanczos, both directions) | <= 2 ms | **[to measure] S-03**, reported by `nam_latency()` |
| Cabinet IR (`ConvolverNode`) | 0 audible (direct convolution of the first block) | Web Audio spec |
| Output buffer + driver | 5-15 ms | `AudioContext.outputLatency` |

Target: total round trip <= 20 ms comfortable; 20-30 ms usable; > 30 ms warning (FR-014). The
context keeps `latencyHint: "interactive"`. The resampler is needed because almost all captures are
trained at 48 kHz while the mixer context runs at 44.1 kHz (stems are 44.1 kHz, ADR-016 D8).
Rejected: running the mixer at 48 kHz (every stem would be resampled in the browser, breaking the
bit-identity of 007 renders), running the input in a second 48 kHz context (two clocks drift;
recording alignment breaks).

### R-09 Capture profile licences

Sources: TONE3000 API terms and tone pages; Gitee/GitHub "NAM_models" collections; Hugging Face
NAM-ADS-v1.

- TONE3000 (the main sharing site) lets each creator choose a licence per tone; examples named in
  its terms are "T3K", CC BY and CC BY-NC. Many captures carry "T3K"; its terms were not found in a
  form that clearly allows redistribution, and downloads need an account or the API terms.
- A community collection ("NAM_models", mirrored on Gitee) is labelled GPL-3.0 as a whole; per-file
  creator licences are not recorded. NAM-ADS-v1 (Hugging Face) is CC BY-NC-SA 4.0 and says each
  model keeps its original licence.
- No well-known collection of captures under CC0 or CC BY with per-file attribution was found.

Consequences (ADR-0212 D4): captures are model weights under ADR-009; the curated catalogue admits
only entries that (1) can be downloaded anonymously over HTTPS from a stable URL, (2) state a
licence for **that file** (CC0, CC BY, CC BY-SA, MIT, Apache-2.0, GPL as data, CC BY-NC*, or
"no licence stated" per ADR-009 rule 4 only when nothing forbids local use), (3) get a recorded
SHA-256, creator and URL in `docs/THIRD-PARTY-LICENSES.md`. Entries are curated in Phase 0
(T004); the target is 6-10 entries (guitar clean, crunch, high gain, overdrive pedal; bass clean,
bass drive). If fewer qualify, the catalogue ships with fewer and the four built-in basic amps
(own MIT code) keep the feature complete. T3K-only captures are not catalogued; users may download
them themselves and upload them as own files (US4).

### R-10 Built-in basic amps and cabinets

Own code, no weights: input high-pass, pre-gain, asymmetric soft clipper (`WaveShaperNode` with a
4x oversampled tanh/asymmetric curve), a three-band tone stack (biquads), post-gain; built-in
cabinet = a short IR synthesised at start-up from a fixed filter recipe (guitar 4x12-like
low-pass 5 kHz + resonance, bass 1x15-like 3.5 kHz). Four presets (guitar clean, crunch, lead,
bass drive). They are fully testable with the mocked `AudioContext` and need no WASM; they also
serve as the fallback when WebAssembly is unavailable.

### R-11 Recording dry and wet

015 records from the input node (assumed API: a recorder worklet on the input). 021 adds a second
tap after the rig, recorded by the same worklet in the same render quantum, so dry and wet are
sample-aligned by construction and share 015's latency compensation. The wet tap is taken after the
chain's own latency is compensated (the resampler delay is subtracted by dropping that many frames
at the start of the wet file). Storage: two FLAC files per take (wet only when the amp was on),
plus a rig snapshot JSON. Re-amp plays the dry file through a rig in the mixer (same engine node
graph as monitoring, input = take buffer instead of the device).

## Part C - DAW export (C11)

### R-12 DAWproject format

Sources: <https://github.com/bitwig/dawproject> README, `Project.xsd`, `MetaData.xsd`,
`Reference.html`.

- Licence: MIT. Format version **1.0, "stable"** (README); no release tags are published, so the
  vendored XSD files are pinned by commit and SHA-256 (T005).
- Container: ZIP with `project.xml` and `metadata.xml`; media and plug-in files in any folder
  chosen by the exporter (example `audio/<name>.wav`); audio may be embedded or referenced
  (`FileReference path`, `external` flag).
- `Project` (`version` required) -> `Application` (name, version), `Transport` (`Tempo` realParameter
  with unit `bpm`, `TimeSignature` numerator/denominator), `Structure` (Tracks with `Channel`:
  `role`, `audioChannels`, `solo`, `Volume`, `Pan`, `Mute`, `Sends`, `Devices`), `Arrangement`
  (`Lanes` with `timeUnit` beats|seconds, `Markers` of `Marker time/name/color`, `TempoAutomation`
  and `TimeSignatureAutomation` as `Points` with `RealPoint`/`TimeSignaturePoint`).
- `Clip`: `time` (required), `duration`, `playStart`, `playStop`, `loopStart`, `loopEnd`,
  `fadeInTime`, `fadeOutTime`, `contentTimeUnit`, `fadeTimeUnit`; content `Audio` (`channels`,
  `sampleRate`, `duration`, `algorithm`, `File`), optional `Warps`.
- Built-in devices: `Equalizer` (bands with `type` highPass|lowPass|bandPass|highShelf|lowShelf|
  bell|notch, `Freq`, `Gain`, `Q`, `Enabled`, `order`), `Compressor` (Attack, Release, Ratio,
  Threshold, InputGain, OutputGain, AutoMakeup), `NoiseGate`, `Limiter`. There is **no built-in
  reverb**.
- The README lists no audio formats; the examples use WAV. Decision: WAV default, FLAC optional
  with a warning (ADR-0213 D4).

### R-13 DAW support

README list (DAWproject 1.0): Bitwig Studio 5.0.9+, PreSonus Studio One 6.5+, Steinberg Cubase 14+,
Cubasis 3.7.1+, VST Live 2.2+, n-Track Studio 10.2.2+; converters DawVert and ProjectConverter
(Reaper). **Ableton Live is not listed** and has no native DAWproject import; MoSCoW C11 named it,

Whether each DAW imports every element (markers, tempo automation, EQ/compressor) is not stated;
owner checks with Bitwig and Studio One (quickstart Q9) record what each shows, and the help topic
lists the result.

### R-14 Timing model of the export

- Lanes use `timeUnit="seconds"`; clips are placed in seconds and carry no `Warps` and no stretch
  `algorithm`, so DAWs play the audio exactly as rendered (no time-stretch).
- The tempo map is `TempoAutomation` with one `RealPoint` per bar (interpolation `hold`), the
  local BPM = beats per bar x 60 / bar duration from the beat grid; `Transport/Tempo` = the first
  bar's tempo. Option `tempoMode: constant` writes only the median BPM (for DAWs that ignore tempo
  automation). Bar 1 starts at the first downbeat; audio before it (pickup) stays at its seconds
  position, so the DAW grid lines up with the song's bars.
- Markers: one per section (014) at the section start (seconds), name = section label, colour from
  the 014 palette; with an arrangement, at the arranged positions.
- Arrangement (019): its edit list (ordered segments of source ranges, repeats, cuts) becomes clips:
  for every segment and channel one `Clip time=<arranged start> duration=<len> playStart=<source
  start>` referencing the same audio file (no re-render; small file). Fades of 019 map to
  `fadeInTime`/`fadeOutTime` with `fadeTimeUnit="seconds"`.
- Mapping of mix settings is in [contracts/dawproject-mapping.md](contracts/dawproject-mapping.md).

### R-15 Building and validating in .NET

- `System.Xml` (`XmlWriter`) and `System.IO.Compression.ZipArchive` are in the .NET 10 BCL; no new
  NuGet package. `XmlSchemaSet` + `XmlReaderSettings { ValidationType = Schema }` validates XSD 1.0
  (the DAWproject XSDs are XSD 1.0). The XSD files are embedded resources of `StemStudio.Domain`
  (MIT licence text kept next to them).
- Audio files come from the 007 render path in `raw` mode (unity gain, centre, no master): WAV
  24-bit, or FLAC/WAV 16 as options. One render job per channel (light lane, ADR-016 D6); the API
  streams them into the ZIP with `CompressionLevel.NoCompression` for audio (already dense) and
  `Optimal` for XML. Size estimate: channels x duration x 44,100 x 2 x 3 bytes (6 stems x 4:22 at
  24-bit = 415 MB); the 007 free-disk guard uses estimate x 2 (renders + ZIP) + 1 GiB.
- Rejected: building the ZIP in the worker (the API owns mixes, arrangement, sections and the
  mapping; the worker only sums audio, ADR-016 D3); a DAWproject library (none for .NET; the Java
  reference library would need a JVM).
