# Data Model: StemStudio MVP (Phase 1)

Wire shapes are defined by the contracts (`contracts/*.openapi.yaml`); this document defines the
domain entities, validation rules, state machines and on-disk layout behind them. Limits are also
available as code: `StemStudio.Contracts.ContractLimits`, `stemstudio_worker.config.WorkerSettings`.

## 1. Backend entities (SQLite via EF Core)

### Track (aggregate root)

| Field | Type | Rules |
|---|---|---|
| `Id` | Guid | PK, generated by the API |
| `SourceType` | enum `Youtube`\|`Spotify`\|`Upload` | stored as string |
| `SourceKey` | string (<= 80) | **unique index**; `youtube:<11-char id>`, `spotify:<22-char base62 id>`, `upload:<64 lower-hex sha256>` |
| `SourceUrl` | string? (<= 2048) | the URL as submitted (null for uploads) |
| `Title` | string (1..500) | initially the URL or the upload file name without extension; replaced by worker metadata title when available |
| `Artist` | string? (<= 500) | from worker metadata |
| `Status` | enum `TrackStatus` | see state machine 3.1 |
| `Stage` | string? (<= 200) | human-readable, from worker |
| `Progress` | int 0..100 | never decreases within one job |
| `Error` | string? (<= 1000) | set iff `Status == Failed` |
| `WorkerJobId` | string? (32 hex) | current worker job |
| `UploadFileName` | string? | file kept under `uploads/` until completed (needed for retry) |
| `DurationSeconds` | double? | > 0 and <= 900 once completed |
| `Model` | string? | `htdemucs_6s` \| `htdemucs` \| `fake` once completed |
| `Stems` | owned collection (JSON) of `Stem` | empty until completed |
| `BeatGrid` | owned (JSON), nullable | set when completed |
| `CreatedAt`, `UpdatedAt` | UTC timestamp | see SQLite note below |

**Stem** (owned by Track): `Name` (`vocals|drums|bass|guitar|piano|other`, unique within the
track), `SizeBytes` (>= 0). The file path is derived, never stored:
`<DataDir>/tracks/<TrackId>/stems/<Name>.flac`. Display order is the order of
`StemNames.SixStem`.

**BeatGrid** (owned value object): `Bpm` (0..400; 0 = detection failed), `Beats` (seconds,
strictly ascending, >= 0), `Downbeats` (subset of `Beats`), `BeatsPerBar` (1..12, default 4),
`Confidence` (0..1), `Reliable` (bool).

**SourceKey parsing** (Domain, used by the API before calling the worker):

| Input | Accepted forms | Key |
|---|---|---|
| YouTube | hosts `youtube.com`, `www.youtube.com`, `m.youtube.com`, `music.youtube.com` with `/watch?v=<id>` or `/shorts/<id>`; `youtu.be/<id>` | `youtube:<id>` (`[A-Za-z0-9_-]{11}`) |
| Spotify | host `open.spotify.com`, path `/track/<id>` or `/intl-<xx>/track/<id>` | `spotify:<id>` (`[A-Za-z0-9]{22}`) |
| Upload | extension `.mp3`/`.wav`/`.flac` (case-insensitive), 1 byte .. 200 MiB (209,715,200 bytes) | `upload:<sha256 of bytes>` |

Binding test vectors (accepted forms with expected key and canonical URL, rejected forms):
[contracts/source-url-vectors.json](contracts/source-url-vectors.json). The API forwards the canonical
URL (`https://www.youtube.com/watch?v=<id>`, `https://open.spotify.com/track/<id>`) to the worker.

Rejected (400 with an actionable message): other hosts, non-https/http schemes, `list=`-only or
`/playlist`, `/album/`, `/artist/`, `/episode/`, `/show/` URLs, missing ids. A `watch?v=<id>&list=...`
URL is accepted as the single video `<id>`.

### Mix (aggregate root)

| Field | Type | Rules |
|---|---|---|
| `Id` | Guid | PK |
| `TrackId` | Guid | FK -> Track (restrict; tracks are not deletable in the MVP) |
| `Name` | string | trimmed, 1..100 chars |
| `NormalizedName` | string | `Name.Trim().ToUpperInvariant()`; **unique index (`TrackId`, `NormalizedName`)** -> 409 |
| `MasterVolume` | double | 0..1, default 1.0 |
| `Channels` | owned collection (JSON) of `ChannelSettings` | at most one per stem; every `Stem` must exist on the track |
| `Metronome` | owned (JSON) `MetronomeSettings` | required |
| `Loop` | owned (JSON) `LoopRegion`, nullable | |
| `CreatedAt`, `UpdatedAt` | UTC timestamp | `UpdatedAt` changes on PUT |

**ChannelSettings**: `Stem` (name), `Volume` 0..1 (default 0.8), `Pan` -1..1 (default 0), `Mute`,
`Solo` (default false). Stems of the track without an entry use the defaults.

**MetronomeSettings**: `Enabled` (default = `BeatGrid.Reliable`), `Volume` 0..1 (default 0.7),
`BpmOverride` null or 30..300, `OffsetMs` -2000..2000 (default 0), `BeatsPerBar` 1..12 (default
`BeatGrid.BeatsPerBar` or 4).

**LoopRegion**: `Start` >= 0, `End` > `Start`, `End` <= `Track.DurationSeconds`, `Enabled`.

**Duplicate**: copy of settings with name `"<name> (copy)"`, then `"<name> (copy 2)"`, ... until
unique; the base name is truncated so the result is <= 100 characters.

**Ordering**: `GET /api/tracks` and `GET /api/mixes` return items ordered by `UpdatedAt`
descending.

**SQLite note**: EF Core's SQLite provider cannot translate ordering/comparison on
`DateTimeOffset`. Store timestamps as UTC `DateTime` (or convert `DateTimeOffset` to ticks with a
value converter) and map to `DateTimeOffset` (offset 0) in the DTOs.

Validation failures produce `400` `ValidationProblemDetails` whose `errors` keys use the JSON
paths of the request (e.g. `settings.metronome.bpmOverride`, `settings.loop.end`).

## 2. Worker entities (JSON files)

### Job

Wire shape: `Job` in `worker-api.openapi.yaml` / `schemas.Job`. Persisted in
`jobs/<jobId>.json` together with internal fields (input file path, normalised audio SHA-256,
cache hit flags) owned by the stem-separation agent. `jobId` = `uuid4().hex`.

### JobResult (`result.json`)

`schemas.JobResult`: `metadata`, `durationSeconds`, `sampleRate` 44100, `channels` 2,
`audioSha256`, `model`, `stems[]` (`name`, `path`, `sizeBytes`), `beatGrid`, `completedAt`.

### Pipeline value types (`ports.py`)

`SourceInfo` (resolved source + key), `NormalizedAudio` (WAV path, duration, sha256),
`SeparationResult` (model, stem name -> FLAC path). Errors: `WorkerError` subclasses
(`InvalidSourceError`, `SourceUnavailableError`, `AudioTooLongError`, `AudioDecodeError`,
`SeparationError`); the message becomes the job `error` text.

## 3. State machines

### 3.1 Track (backend)

```text
            create (import)                      worker status (forward only)
   [none] ─────────────────> queued ──> downloading ──> separating ──> analysing ──┐
                               │  │          │               │             │        │ result + all stems
                               │  └──────────┴──── (any forward skip) ─────┴────────┤ stored locally
                               │                                                     v
                               │                                                completed  (terminal)
                               │ any non-terminal: worker failed | worker 404 |
                               │ worker job unknown after restart | stem download failed
                               v
                            failed (terminal) ── POST /api/tracks/{id}/retry ──> queued (new WorkerJobId)
```

Rules:
- The API only moves forward in the order queued < downloading < separating < analysing <
  completed; skipped states are allowed (e.g. a worker cache hit goes queued -> completed).
- `completed` is set only after the result and every stem file were written (write to a temp
  file, then rename); otherwise the track becomes `failed` with a readable reason.
- `Progress` is copied from the worker; `completed` forces 100.
- Worker unreachable while polling: keep the state and retry (no failure); worker `404` for the
  job: `failed` "interrupted by restart".
- Retry is allowed only from `failed`; for uploads only while the uploaded file still exists
  (else 409).

### 3.2 Worker job

```text
 queued ──> downloading ──> separating ──> analysing ──> completed
   │            │               │              │
   └────────────┴───────────────┴──────────────┴──────> failed      (WorkerError message, or
                                                                     "interrupted by restart" at start-up,
                                                                     or "Unexpected error" + log for bugs)
```

| Status | Progress range | Stage text (examples) |
|---|---|---|
| queued | 0 | "Queued" |
| downloading | 0-10 | "Downloading audio" (URL), "Preparing audio" (ffmpeg normalise, also uploads) |
| separating | 10-90 | "Separating stems" (`10 + 80 x fraction`) |
| analysing | 90-99 | "Analysing beats" |
| completed | 100 | "Completed" |
| failed | unchanged | "Failed" |

Fixed error texts (asserted verbatim by tests; other `WorkerError` messages are free text but
must be readable and free of secrets):

| Cause | `error` |
|---|---|
| Duration > 900 s (`AudioTooLongError`) | "Audio is longer than 15 minutes" |
| Non-terminal job found at start-up | "interrupted by restart" |
| Spotify track without YouTube match | "No matching YouTube audio was found for this Spotify track." |
| Unexpected exception (bug) | "Unexpected error" |

Cache hit by source key: queued -> completed directly. Cache hit by audio SHA-256 after
normalisation: downloading -> completed (separation and analysis reused).

## 4. Storage layout

```text
<StemStudio:DataDir>/                 # API (default ../../data/api, compose: /data)
├── stemstudio.db                     # SQLite (EF Core migrations applied at start-up)
├── uploads/<sha256><ext>             # kept until the track completes (retry source)
└── tracks/<trackId>/stems/<name>.flac

<STEMSTUDIO_DATA_DIR>/                # worker (default data/worker, compose: /data)
├── jobs/<jobId>.json                 # job state (atomic replace)
├── work/<jobId>/                     # temporary download + normalised WAV; deleted when terminal
├── uploads/<jobId>/input<ext>        # received upload (<ext> = .mp3|.wav|.flac, lower-case); deleted when terminal
└── cache/
    ├── by-source/<source_key with ':' replaced by '_'>.json   # {"audioSha256": "..."}
    └── by-audio/<audioSha256>/{result.json, stems/<name>.flac}
```

Path safety: every path component is generated (GUID, hex job id, hex hash, enum stem name);
user-supplied file names are never used as path components.
