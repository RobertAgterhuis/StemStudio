# Feature Specification: Tablet and Remote

**Feature Branch**: `018-tablet-remote`

**Created**: 2026-11-16

**Status**: Draft (architect; contract numbers fixed by the roadmap allocation, reconciled with the
014 contracts in Phase 0)

**Input**: MoSCoW item **C4** (`docs/MoSCoW.md`): "Tablet layout and installable app (PWA) for the
music stand, controlled over the home network. Practising usually happens away from the desk.
Responsive work exists (320 px); add PWA manifest and a LAN-safe 'remote' mode." Roadmap
(`docs/ROADMAP.md`): feature 018, depends on 014 (practice flow: sections, score follows playback,
setlists, keyboard/foot-pedal shortcuts); contracts backend-api **1.17.0**, ui-test-ids
**1.17.0**, new **remote-protocol 1.0.0**. Constraints: local and single-user (constitution),
W2 "no multi-user hosting over the internet", every instrument counts equally (MoSCoW principle).

## Clarifications

### Session 2026-11-16

Answered autonomously by the architect (operating mode: fully autonomous). Rationale in
[research.md](research.md) and [ADR-027](../../docs/decisions/ADR-027-tablet-remote-lan-security.md).
Everything that changes network exposure is opt-in and listed in the hand-off report.

- Q: Which device plays the audio? → A: **always the main device**: the computer that runs
  StemStudio, in its browser tab on `localhost`. A phone or tablet is a **remote**: it sends
  commands and shows the music-stand view, it never receives stems and never plays audio. Audio on
  the tablet would need the full app and the stems on the network (out of scope, see Won't).
- Q: What exactly is reachable from the home network? → A: only the **remote surface**: a small
  separate web page (the remote client), its static files, a pairing endpoint, one WebSocket for
  commands and state, and read-only content of the song the main device has open (lyrics, chords,
  sections, sheet-music PDFs, artwork). The StemStudio app itself (Blazor UI), the API and the
  worker are **never** reachable from the network. The remote surface runs on its own port,
  which exists only when remote mode is set up.
- Q: Is it on by default? → A: **No. Two separate opt-ins.** (1) Set-up: the owner starts
  StemStudio with remote mode configured (`docker-compose.lan.yml` with the computer's LAN
  address, or the matching settings on the non-Docker path); without that there is no extra open
  port at all. (2) In the app: the switch "Allow remote control" on the Remote control page (off
  by default). Turning the switch off disconnects every remote within one second.
- Q: Is the app reachable from the network today? → A: **Possibly, by accident**: the compose file
  publishes 8080 and 8081 on all host interfaces. Feature 018 changes the default to
  `127.0.0.1` (configurable for special set-ups with `STEMSTUDIO_BIND_ADDRESS`) and restricts the
  accepted host names, so only the remote surface can ever be reached from the LAN. This is a
  deliberate exposure **reduction** and is flagged in the report.
- Q: How does a device get permission? → A: **pairing with human approval**. On the computer the
  owner clicks "Pair a device"; StemStudio shows a 6-digit code, a QR code with the remote
  address, and the time left (2 minutes). On the tablet the owner scans the QR (or opens the
  address and types the code) and enters a device name. The computer then shows "Allow
  <device name>?" together with a 3-digit check number that the tablet shows too; only after
  **Allow** does the tablet receive its device key. Codes are single-use; five wrong codes end the
  pairing window.
- Q: How long does a paired device stay paired? → A: until it is removed on the computer, or 30
  days without use. At most 8 paired devices and 4 connected at once. Removing a device (or
  "Remove all") disconnects it within one second.
- Q: HTTPS or HTTP on the home network? → A: **Both modes, HTTPS recommended**:
  - `lan-https`: the owner creates a certificate for the computer's LAN address with
    **mkcert** (open-source, BSD-3-Clause, run by the owner, not shipped with StemStudio) and
    installs mkcert's root certificate on the tablet. This gives a secure context, so the tablet
    can install the remote as an app, keep the screen awake and show the shell offline.
  - `lan-http`: no certificate needed; the remote works for control and the stand view, but the
    connection is not encrypted, the tablet cannot install it as an app and cannot keep the
    screen awake. The Remote control page and the remote show "Not encrypted" in this mode.
  - Rejected: a certificate generated by StemStudio and accepted by clicking through browser
    warnings (service workers do not run on certificate errors and it trains people to ignore
    warnings), a CA built into StemStudio (it would hold a root key), public certificates or
    tunnels (need the internet, W2).
- Q: What can a remote do? → A: a fixed list of practice commands: play, pause, stop, seek,
  skip, previous/next section, loop a section, loop on/off, tempo (012), count-in and metronome
  on/off, mute/solo per stem and "practise my part" per instrument family, master volume, setlist
  previous/next and open a song from the library or setlist (the computer opens it). Nothing that
  deletes, imports, saves, exports, generates or talks to the agent.
- Q: What does the music-stand layout show? → A: a large view of the open song's content for the
  chosen part: lyrics (synced lines, 006), chords (016), sheet music and tablature PDFs (008/016)
  and sections (014), with big transport buttons, a position bar and the current section. It
  works in landscape and portrait, keeps the screen awake while it is shown (where the browser
  allows it) and is available in two places: on the computer as the **Stand view** of the mixer,
  and on the tablet as the **Stand** tab of the remote.
- Q: Every instrument counts equally - what does that mean here? → A: the part picker of the stand
  view lists every instrument family that has content for the song (vocals, guitar, bass, keys,
  drums, other); the remote's Mix tab has a "practise my part" button and mute/solo for every
  family. Acceptance tests cover one case per family.
- Q: What is the installable app (PWA)? → A: a web app manifest, icons and a service worker that
  caches only the **app shell** (an offline page, styles, fonts, icons). When StemStudio is not
  running, the installed app shows "StemStudio is not running" with how to start it. Audio,
  stems, API data and Blazor traffic are never cached. On the computer the app installs from
  `http://localhost:8080` (browsers treat `localhost` as secure); on the tablet the remote
  installs only in `lan-https` mode.
- Q: Who sees what (004 journey levels)? → A: Beginner: Stand view button, install hint, and the
  Remote control page only when remote mode is set up. Advanced: plus the Remote control page with
  the "not set up" explanation, device rename. Expert: plus the remote audit log (pairings,
  failed codes, removals) and connection details. The remote client itself has one simple layout.
- Q: Does the composer agent (011) get remote tools? → A: No (not needed; recorded as Won't).
- Q: Languages? → A: English UI texts, like the rest of the app (Dutch UI is Won't, MoSCoW).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Music-stand layout on the computer (Priority: P1)

A musician opens a song in the mixer and switches to **Stand view**: the screen shows the chosen
part's content (lyrics, chords, sheet music or tablature) large and readable from a distance, the
current section, a position bar, and big transport buttons (play/pause, back, previous/next
section, loop). The layout adapts to landscape and portrait and the screen stays on while it is
shown.

**Why this priority**: it helps every musician at once, works without any network change, and it is
the view the tablet will show too.

**Independent Test**: open a fake-separated song with lyrics, chords and a score; toggle Stand
view; check the layout at 1280x800, 1024x768 and 768x1024, play, jump to the next section, and
verify that the wake lock is requested and released.

**Acceptance Scenarios**:

1. **Given** an open mixer with a completed track, **When** the user clicks Stand view, **Then**
   the mixer controls fold away, the content area fills the screen, the transport buttons are at
   least 64 x 64 CSS px, and playback continues without interruption.
2. **Given** the stand view, **When** the user picks a part (for example Drums), **Then** only the
   content kinds that exist for that family are offered (for drums: the drum score; for vocals:
   lyrics and the melody score), and the choice is remembered for the next song.
3. **Given** the stand view while playing, **When** the position moves, **Then** the current lyric
   line, chord and score page follow the playback (score follow from 014) and the section name
   updates.
4. **Given** a browser that supports the Screen Wake Lock API, **When** the stand view is shown,
   **Then** the screen is kept on and released when the user leaves the stand view or the tab is
   hidden; the toggle "Keep screen on" shows `on`, `off` or `unsupported`.
5. **Given** the window is turned from landscape to portrait, **When** the layout changes,
   **Then** content stays above the transport, nothing overlaps, and there is no horizontal
   scrolling down to 320 px wide.

---

### User Story 2 - Pair a phone or tablet safely (Priority: P1)

The owner wants to control StemStudio from the music stand. On the computer the owner opens
**Remote control**, turns on "Allow remote control", clicks **Pair a device**, and scans the QR
code with the tablet. The tablet asks for a device name, shows a check number, and the computer
asks "Allow 'iPad music stand'? Check number 417". After **Allow**, the tablet is connected. The
owner can rename or remove devices at any time.

**Why this priority**: remote control is the point of C4, and it is safe only when pairing is.

**Independent Test**: with remote mode `lan-http` on the fake stack, pair a second browser context
by code, approve, verify the device is listed; remove it and verify the context is disconnected
within one second; verify a wrong code five times ends the pairing.

**Acceptance Scenarios**:

1. **Given** StemStudio started without remote mode, **When** the user opens Remote control,
   **Then** the page says remote control is not set up, links to the manual, the switch is
   disabled, and no additional port is open on the computer.
2. **Given** remote mode is set up and the switch is off, **When** a device opens the remote
   address, **Then** it shows "Remote control is off on the computer" and pairing and control are
   refused.
3. **Given** the switch is on, **When** the owner clicks Pair a device, **Then** a 6-digit code,
   a QR code with the remote address and a 2-minute countdown are shown; starting a new pairing
   ends the previous one.
4. **Given** an open pairing window, **When** a device enters the right code and a name, **Then**
   both screens show the same 3-digit check number and the computer asks to allow the device;
   **Allow** gives the device access, **Reject** ends the pairing and the device shows "Not
   allowed".
5. **Given** an open pairing window, **When** five wrong codes are entered (from any device),
   **Then** the window closes, the computer shows "Pairing stopped after 5 wrong codes" and the
   audit log records it.
6. **Given** a paired device, **When** the owner removes it (or all devices) on the computer,
   **Then** its connection closes within one second and it must pair again.
7. **Given** `lan-http` mode, **When** the Remote control page or the remote is shown, **Then**
   it states "Not encrypted: anyone on your network could read this connection" and links to the
   HTTPS set-up.

---

### User Story 3 - Control playback from the paired device (Priority: P1)

On the paired phone or tablet the musician sees the song that is open on the computer, its
position, section, tempo, loop and the stems. The musician taps play, jumps to the chorus, loops
the bridge at 80 % tempo, mutes their own instrument ("practise my part") and the computer plays
accordingly, with the computer's screen updating too.

**Why this priority**: this is the remote control itself.

**Independent Test**: two browser contexts (computer and remote) on the fake stack; from the
remote: play, seek, next section, loop section, tempo 80 %, mute bass, solo vocals; assert the
main context's engine state and the remote's state after each command, within the latency budget.

**Acceptance Scenarios**:

1. **Given** a connected remote and a mixer open on the computer, **When** the remote taps Play,
   **Then** the computer starts playback within 250 ms (p95, home Wi-Fi; 150 ms on loopback) and
   the remote shows "playing" with a moving position.
2. **Given** a playing song, **When** the user changes something on the computer (pause, fader,
   section), **Then** every connected remote shows the new state within 200 ms.
3. **Given** two connected remotes, **When** both send commands, **Then** the commands are
   applied in arrival order and both remotes show the same resulting state.
4. **Given** no mixer is open on the computer, **When** the remote is connected, **Then** it shows
   "No song open on the computer" and offers the library and setlist (US6); transport buttons are
   disabled.
5. **Given** the mixer of each instrument family (vocals, guitar, bass, keys, drums, other),
   **When** the remote taps "practise my part" for that family, **Then** exactly that family's
   stems are muted on the computer and the button shows the active state; tapping again restores
   the previous mute states.
6. **Given** an invalid or unknown command (for example tempo 300 %, an unknown stem, or a
   command not in the list), **When** it is sent, **Then** nothing changes and the remote shows a
   short reason.
7. **Given** the Wi-Fi drops for a few seconds, **When** it returns, **Then** the remote reconnects
   by itself (backoff up to 10 s) and shows the current state; commands sent while offline are not
   replayed.

### User Story 4 - Music-stand view on the tablet (Priority: P2)

The tablet on the music stand shows the same stand view as the computer: lyrics, chords or sheet
music of the chosen part, large, following the computer's playback, with big transport buttons
that act as the remote. In HTTPS mode the screen stays on.

**Why this priority**: makes the tablet useful as the actual music stand; builds on US1 and US3.

**Independent Test**: second context on the remote Stand tab; play on the computer; verify the
current lyric line, chord and sheet page follow the position; switch part for every family that
has content.

**Acceptance Scenarios**:

1. **Given** a connected remote, **When** the user opens the Stand tab, **Then** the part picker
   lists every family with content for the open song and the content follows the main device's
   position within 200 ms.
2. **Given** a sheet-music PDF for the chosen part, **When** playback crosses a page boundary
   known from 014's score map, **Then** the next page is shown; without a score map the user turns
   pages with big buttons or swipe.
3. **Given** `lan-https` mode, **When** the Stand tab is visible, **Then** the screen wake lock is
   held (where supported) and released when hidden; in `lan-http` mode the toggle says
   "unavailable without HTTPS".
4. **Given** the song on the computer changes, **When** the remote is on the Stand tab, **Then**
   the content reloads for the new song within 2 seconds and the part choice is kept when that
   family has content.
5. **Given** the content of the song, **When** it is shown on the remote, **Then** only the open
   song's content is accessible; requests for other tracks or assets are refused.

---

### User Story 5 - Install StemStudio as an app (Priority: P2)

The owner installs StemStudio as an app on the computer (from `localhost`) and the remote as an app
on the tablet (in HTTPS mode), so each opens full-screen from the home screen or start menu. When
StemStudio is not running, the installed app shows a friendly offline page instead of a browser
error.

**Why this priority**: convenience; it does not change what the app can do.

**Independent Test**: Lighthouse/Playwright installability checks for the main app on localhost and
the remote on a secure origin; stop the stack and reload: the offline page appears within 2 s;
verify that no stem, API or `_blazor` request is answered from the cache.

**Acceptance Scenarios**:

1. **Given** a browser that offers installation, **When** the user opens StemStudio on localhost,
   **Then** an "Install app" button is shown in the shell (and hidden after installation or when
   the browser offers no install).
2. **Given** the installed app and StemStudio stopped, **When** the app is opened, **Then** the
   offline page says StemStudio is not running and how to start it; when the server is back,
   "Try again" opens the app.
3. **Given** the installed app, **When** stems are played, an API call is made, or the Blazor
   circuit connects, **Then** none of these responses comes from the service worker's cache.
4. **Given** a new StemStudio version, **When** the app is opened, **Then** the new shell is used
   after at most one reload (no stale shell).
5. **Given** `lan-https` mode on the tablet, **When** the user installs the remote, **Then** it
   opens full-screen at `/remote/` with its own name and icon ("StemStudio Remote"); in
   `lan-http` mode the remote explains that installing needs HTTPS.

---

### User Story 6 - Choose the song and walk through a setlist from the remote (Priority: P3)

From the remote the musician picks the next song in the setlist (014) or searches the library, and
the computer opens that song's mixer; "next song" in a setlist works from the remote's big button.

**Why this priority**: useful for band and set practice, but the computer can do it too.

**Independent Test**: create a setlist of three fake tracks; from the remote tap Next song twice;
verify the computer's mixer opens each track and the remote's stand content follows.

**Acceptance Scenarios**:

1. **Given** a connected remote and a StemStudio tab open on the computer (any page), **When** the
   remote chooses a song, **Then** the computer opens that song's mixer within 2 seconds, unless
   the mixer has unsaved changes, in which case the computer asks and the remote shows "Waiting
   for the computer".
2. **Given** an active setlist, **When** the remote taps Next song at the end of the setlist,
   **Then** nothing happens and the button is disabled at the last song.
3. **Given** the library on the remote, **When** the user searches, **Then** only titles, artists
   and durations of completed tracks are shown (no file names, paths or lyrics).

### Edge Cases

- **The computer's LAN address changes** (DHCP): the remote surface stays bound to the configured
  address and is unreachable; the Remote control page shows "Remote address not available on this
  computer" and the manual recommends a DHCP reservation. Certificates name the address, so a new
  address needs a new certificate.
- **The laptop joins another network** (café, hotel): binding to a specific address means the
  remote surface is not reachable there unless the address happens to be the same; then the host
  name check, the in-app switch, pairing and device keys still apply.
- **Certificate missing, expired, unreadable or not valid for the configured address** in
  `lan-https` mode: StemStudio does **not** fall back to HTTP; the web app starts without the
  remote surface and the Remote control page shows the reason. Expiry within 30 days shows a
  warning.
- **Two mixer tabs on the computer**: one tab is the remote's player at a time: the one that
  played or was focused last; the other shows "Remote controls another tab".
- **Main tab closed or reloaded**: the remote shows "No song open on the computer" and recovers
  when a mixer opens.
- **Unsaved mixer changes**: remote commands change the live mix like the computer's own controls;
  nothing is saved from the remote.
- **Remote opened on the computer itself** (on the remote address): works like any remote device
  after pairing; no special trust.
- **Device name with markup or very long**: names are 1-40 printable characters, shown as text
  only; longer input is refused.
- **Server restarts**: pairing windows end; paired devices keep their keys and reconnect.
- **Revoked or switched off while connected**: the remote shows "Removed on the computer" or
  "Remote control is off" and stops reconnecting until the user opens it again.
- **More than 4 connections or 8 devices**: the extra connection is refused with "Too many
  remotes"; a new pairing beyond 8 devices asks to remove one first.
- **Flooding**: more than 20 commands per second from one connection, messages over 4 KB or
  malformed messages close that connection; the device can reconnect.
- **Clock differences between devices**: positions are sent with the server's time base and the
  remote interpolates locally; no device clock is trusted.
- **Wi-Fi with client isolation** (guest networks): devices cannot reach each other; the manual
  says so.
- **iOS in `lan-http` mode**: no wake lock and no install; the remote still works for control.
- **014 or 016 content missing for a song**: the stand view offers what exists; with nothing to
  show it shows the section list and position only.
- **Score follow without a score map**: manual page turning.
- **Browser without WebSocket or with blocked storage**: the remote shows an explanation; with
  blocked storage the device must pair again after the browser closes.

## Requirements *(mandatory)*

### Functional Requirements

**Stand view (computer)**

- **FR-001**: The mixer MUST offer a Stand view that shows, for the open track, a large content
  area (lyrics, chords, sheet/tab PDF, sections) for a chosen part, the current section, a
  position bar and transport buttons (play/pause, back to start of section, previous/next section,
  loop current section) of at least 64 x 64 CSS px; other mixer controls are hidden but keep
  their state.
- **FR-002**: The part picker MUST list every instrument family that has content for the track
  (vocals, guitar, bass, keys, drums, other) in the same order and with equal prominence; the
  chosen family is remembered per browser.
- **FR-003**: Content MUST follow playback: lyric line (006), chord (016), score page/measure
  (014 score follow) and section (014). Absent content kinds are not offered.
- **FR-004**: The stand layout MUST work in landscape and portrait from 320 px wide to 2560 px,
  with no horizontal scroll, and offer a text size setting (100-200 %).
- **FR-005**: While the stand view is visible, StemStudio MUST request a screen wake lock where the
  browser supports it, re-acquire it when the page becomes visible again, release it on exit, and
  show its state (`on`, `off`, `unsupported`); the user can turn it off.

**Installable app**

- **FR-006**: The web app MUST provide a web app manifest (name, short name, icons 192/512 and
  maskable, `start_url` `/`, `scope` `/`, `display` `standalone`, theme colours from the 004
  tokens) and a service worker that precaches only the shell (offline page, CSS, fonts, icons).
- **FR-007**: The service worker MUST NOT cache or answer requests for `/_blazor`, `/_framework`,
  API origins, stems, artwork, assets or any cross-origin URL; navigations are network-first with
  the offline page as fallback; a new version replaces the shell at the next load.
- **FR-008**: The shell MUST show an "Install app" button only when the browser offers
  installation and hide it once installed.
- **FR-009**: The remote client MUST have its own manifest (`scope` and `start_url` `/remote/`,
  name "StemStudio Remote") and service worker with the same shell-only rule; installation and
  wake lock are offered only in a secure context.

**Remote mode set-up and exposure**

- **FR-010**: Remote mode MUST be off unless configured at start-up (`StemStudio__Remote__Mode` =
  `lan-https` or `lan-http`, default `off`). With `off`, the web app MUST NOT open any listener
  other than its main port.
- **FR-011**: The default compose set-up MUST publish the web (8080) and API (8081) ports on
  `127.0.0.1` only (override with `STEMSTUDIO_BIND_ADDRESS`); remote mode is added with
  `docker-compose.lan.yml`, which requires `STEMSTUDIO_LAN_ADDRESS` (no default) and publishes only
  the remote port on that address. The API is never published on the LAN.
- **FR-012**: Start-up MUST fail the remote surface (not the app) when the configured LAN address
  or public host is not a private, link-local or loopback address (RFC 1918, RFC 4193, RFC 3927,
  loopback) or when `lan-https` has no valid certificate for the public host; there is no
  automatic fallback from HTTPS to HTTP.
- **FR-013**: The remote listener MUST serve only the remote surface (remote static files, the
  shared design tokens and fonts, `GET /remote/v1/info`, pairing, the WebSocket, content
  endpoints); every other path, including `/_blazor`, Blazor pages and any API path, MUST return
  404. The main listener MUST NOT serve the remote protocol endpoints.
- **FR-014**: Both listeners MUST accept only configured host names (main: `localhost`,
  `127.0.0.1`, `[::1]`; remote: the public host and configured aliases), answering 400 otherwise
  (DNS rebinding protection). The API MUST accept only `localhost`, `127.0.0.1`, `[::1]` and its
  compose service name.
- **FR-015**: The remote listener MUST check the `Origin` header of the WebSocket upgrade and of
  every state-changing request (exact match with the remote origin) and send security headers:
  a strict Content Security Policy (`default-src 'self'`, no inline script, `frame-ancestors
  'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Cache-Control:
  no-store` on every non-static response.
- **FR-016**: The Remote control page MUST show the mode (`off`, `lan-http`, `lan-https`), the
  remote address, certificate expiry (HTTPS) and, in `lan-http`, the "Not encrypted" warning.

**In-app switch, pairing and devices**

- **FR-017**: "Allow remote control" MUST be off by default, changeable only from the main app;
  when off, the remote listener answers only the static files and `info` (with `enabled: false`)
  and refuses pairing, content and WebSocket connections; switching off closes all remote
  connections within 1 second.
- **FR-018**: Pairing MUST use one pairing window at a time, valid 120 seconds, with a 6-digit code
  from a cryptographic random source and a QR code that encodes the remote address with the code
  in the URL fragment; starting a new window ends the previous one; a code is single-use.
- **FR-019**: A pairing window MUST end after 5 wrong codes; the remote listener MUST limit
  pairing attempts to 20 per minute in total; failures return the same answer for unknown,
  expired and used codes.
- **FR-020**: After a correct code the computer MUST show the device name and a 3-digit check
  number (also shown on the device) and wait for **Allow** or **Reject**; no access is granted
  without Allow; the request expires with the window.
- **FR-021**: On Allow, StemStudio MUST issue a device key of 256 random bits, deliver it exactly
  once to the requesting device, and store only its SHA-256 hash; device keys are never logged,
  shown or returned again.
- **FR-022**: The Remote control page MUST list paired devices (name, paired at, last used,
  connected now, transport http/https) and allow rename (1-40 printable characters), remove, and
  remove all; removal closes that device's connections within 1 second.
- **FR-023**: Device keys MUST expire after 30 days without use; at most 8 paired devices and 4
  simultaneous remote connections.
- **FR-024**: StemStudio MUST record an audit log (last 500 events: pairing started, request,
  allowed, rejected, expired, stopped after wrong codes, device renamed/removed, all removed,
  switch changed, refused authentication) without codes, keys or check numbers; visible to Expert.

**Remote protocol**

- **FR-025**: The remote MUST authenticate on the WebSocket with its device key in the first
  message (never in the URL or a cookie), within 5 seconds of connecting; content requests use
  `Authorization: Bearer`.
- **FR-026**: Commands MUST be limited to the enumerated list of remote-protocol 1.0.0, validated
  (type, range, known ids) before dispatch, and acknowledged with `ok` or a reason; unknown or
  invalid commands change nothing.
- **FR-027**: Remote commands MUST act on the active player (the mixer tab on the computer that
  played or was focused last) through the same handlers as the computer's own controls and 014
  shortcuts; nothing is saved by a remote command.
- **FR-028**: The server MUST push a full state snapshot to every connected remote on every change
  (at most 10 per second) and at least every 2 seconds while playing, with a server time base for
  position interpolation; snapshots are at most 8 KB.
- **FR-029**: Messages over 4 KB, more than 20 commands per second per connection, or malformed
  JSON MUST close the connection with a protocol close code; the remote reconnects with backoff
  (1, 2, 4, 8, 10 s) and never replays commands.
- **FR-030**: Content endpoints MUST serve only content of the track that the active player has
  open (lyrics lines, chord events, sections, sheet/tab PDFs of that track, artwork), read
  through the API server-side; any other id returns 404.
- **FR-031**: "Practise my part" MUST mute exactly the stems of the chosen family and restore the
  previous mute states when released; mute and solo are available for every stem.
- **FR-032**: Opening a song from the remote (US6) MUST go through the computer's open tab, which
  asks first when the mixer has unsaved changes; library results on the remote contain only
  title, artist, duration and id of completed tracks.

**Help, levels, accessibility, docs**

- **FR-033**: New help topics (area `remote`, plus stand view in `mixer` and install in `start`):

### Key Entities

- **Remote settings**: the in-app switch (enabled, changed at).
- **Pairing window** (memory only): code, check number, expiry, wrong-code count, at most one
  device request (name, transport, poll secret), state.
- **Paired device**: id, name, key hash, paired at, last used, transport at pairing.
- **Remote audit event**: time, kind, device id/name, short detail.
- **Player** (web app memory): the active mixer tab and its state snapshot.
- **Remote connection** (web app memory): device, connected at, rate limiter.
- **Stand preferences** (browser): part, content kind, text size, keep screen on.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From a remote tap to the computer's engine change: p95 <= 150 ms on loopback (E2E,
  50 commands) and <= 250 ms on the owner's home Wi-Fi (manual check, reference machine).
- **SC-002**: State changes made on the computer appear on every connected remote within 200 ms
  (p95, loopback E2E); the remote's interpolated position differs from the engine by <= 100 ms.
- **SC-003**: A first-time user pairs a device in at most 30 seconds and 4 actions (open Remote
  control, Pair a device, scan, Allow) in the quickstart walk-through.
- **SC-004**: With remote mode off, a port scan of the computer shows no StemStudio port on any
  non-loopback interface; with remote mode on, only the remote port is reachable, and 100 % of the
  security test list in [plan.md](plan.md) ("Security verification") passes: non-surface paths
  404, foreign host 400, foreign origin 403, no key 4401, revoked key closed within 1 s,
  sixth wrong code refused, flood closed.
- **SC-005**: Lighthouse installability passes for the main app on localhost and for the remote on
  a secure origin; with the stack stopped the installed app shows the offline page within 2 s;
  0 stem, API or `_blazor` responses served from the service worker in the E2E check.
- **SC-006**: Stand view and remote pass axe with 0 serious/critical violations at 1280x800,
  1024x768, 768x1024 and 390x844; no horizontal scroll at 320 px.
- **SC-007**: For each instrument family (vocals, guitar, bass, keys, drums, other) one E2E case
  shows that family's content in the stand view and its "practise my part" on the remote.
- **SC-008**: The wake lock is held while the stand view is visible in a supporting secure context
  and released within 1 s of hiding it (Vitest with a mocked `navigator.wakeLock` plus one
  Chromium E2E check).
- **SC-009**: Coverage >= 90 % line and branch for backend, web, `src/remote-client` and
  `src/web-interop`; SIG limits respected; every OpenAPI contract Redocly-valid (3.1) and the
  message schema validates the example messages.

## Assumptions

- 014 (practice flow) is delivered first: sections, score follow with a page/measure map, setlists
  and the command catalogue used by shortcuts (backend 1.13.0, engine 2.4.0); 012 (tempo,
  count-in) and 016 (chords, tablature, drum views) are delivered too (build order). Names of
  those contracts used here are reconciled in Phase 0; missing content degrades gracefully.
- The owner's devices run current browsers (Chrome/Edge 120+, Safari 17+, Firefox 120+); the home
  network is WPA2/WPA3 without client isolation; the computer has a stable LAN address (DHCP
  reservation recommended).
- mkcert is installed and run by the owner when HTTPS is wanted; StemStudio neither ships nor
  runs it.
- One person uses StemStudio; paired devices belong to that person (single-user constitution).
  Pairing is not multi-user access: every remote acts as the same user, with fewer rights.
- Docker Desktop on Windows can publish a port on one specific host address (verified in Phase 0,
  research R-03); otherwise the non-Docker path is documented.

## Won't have (this feature)

- Audio playback on the tablet or phone, stem download to remote devices, or the full StemStudio
  UI on the network.
- Access from the internet, cloud relays, tunnels, UPnP, accounts or multi-user (W2).
- A certificate authority built into StemStudio; clicking through certificate warnings as a
  supported set-up.
- Remote tools for the composer agent (011); recording (015) controlled from the remote.
- Native apps (W6).

## Cross-feature note: 011 follow-up "claude-key" (architect, 2026-11-16)

Design: `specs/011-ai-composer-agent/followups/claude-key/`. The Claude API key can be stored in
Settings through `PUT`/`DELETE /api/agent/settings/claude-key`, which are local-only (TCP peer
loopback or the `web` service, loopback host names, web origin). For 018 this means:

- No remote command, page or content endpoint reads, writes, deletes or tests a secret; the remote
  protocol stays without secret commands (remote-protocol 1.0.0 unchanged).
- FR-011 (ports on `127.0.0.1`), FR-013 (remote listener 404 for every API path) and FR-014
  (host-name allow-lists) are what make "only on the computer itself" a hard boundary; until 018 the
  follow-up's Web-side check is a host-name guard only (follow-up research R-05, plan.md Q1).
- 018 security tests add: `PUT /api/agent/settings/claude-key` through the remote listener -> 404;
  a paired device's WebSocket has no message type that reaches the key.
